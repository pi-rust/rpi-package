# rpi-packages

Rust-native extension packages for the `rpi` agent, built against the stable
`rpi-plugin-sdk` ABI from `pi-rust`.

The selection was taken from the Pi package catalog on 2026-09-09. Pi does not
publish star ratings in the catalog, so monthly downloads are used as the
objective popularity signal. These three cover the highest-download extensions
that map cleanly onto the current Rust SDK:

| Rust package | Inspired by | Catalog downloads/month | Registered tool |
| --- | --- | ---: | --- |
| `rpi-mcp-adapter` | `pi-mcp-adapter` | 761,442 | `mcp_list`, `mcp_call`, `mcp_request` |
| `rpi-subagents` | `pi-subagents` | 362,483 | `delegate_task` |
| `rpi-lens` | `pi-lens` | 65,476 | `code_lens` |

These are independent Rust implementations, not ports of upstream source code.

The workspace also includes local-first workflow packages: `rpi-todo`
(`todo`), `rpi-goal` (`goal`, a Codex-style persistent, context-injected
objective per project), `rpi-plan-mode` (`/plan`, `plan_mode_start`,
`plan_mode_complete`),
`rpi-codegraph` (`codegraph`),
`rpi-ask-user`, `rpi-permissions`,
`rpi-websearch`, `rpi-webfetch`, plus `rpi-im-message` (`im_message_server`), plus
`rpi-voice`, which adds `/voice` dictation and spoken replies to the running
TUI. Its STT is OpenAI-compatible by default; built with `--features local-stt`
it embeds sherpa-onnx + SenseVoice and runs entirely offline (see
[`packages/rpi-voice/README.md`](packages/rpi-voice/README.md) for the build
either way).

`rpi-acp` (`--acp`) runs rpi as an external agent in Zed (or any Agent Client
Protocol client) over stdio, backing each ACP session with a child
`rpi --mode rpc` process. It claims the process stdio via the plugin ABI's
`ownsStdio` declaration, so see
[`packages/rpi-acp/README.md`](packages/rpi-acp/README.md) for the host
requirement and Zed configuration. **No hand-editing of Zed's `settings.json`
is needed**: `rpi --install-zed` registers it (`rpi --print-zed` just prints the
snippet), and starting `rpi --acp` registers it automatically — idempotent,
comment-preserving; opt out with `RPI_ACP_NO_AUTO_REGISTER_ZED=1`. The same
crate builds a standalone `rpi-acp-bridge` binary (`task pack-acp`) with the same
commands, for clients that launch an ACP agent directly, and as the artifact for
an eventual
[ACP Registry](https://github.com/agentclientprotocol/registry) entry
([`registry/`](registry/README.md)); the bridge owns stdio itself, so it needs
no host support and works with a stock `rpi`.

`rpi-webui` (`--webui=openwebui`) starts Open WebUI and automatically connects
its embedded ACP server to the current project. It installs the UI through uv
when needed, imports/configures its Pipe and selects the project model.
Use `--webui-permission=bypass` or `--webui-workspace <path>` as needed. See
[usage and existing-server setup](packages/rpi-webui/README.md).

## Build and install

`rpi-run-stats` adds a live top-right monitoring panel: rounds, provider steps,
output tok/s, time to first token, response time, rolling 60-second TPM,
input/output/cache tokens, errors and USD cost. Use `/stats on`, `/stats off`
or `/stats` to toggle it, and `/stats position top-left` to move it.
It uses the generic declarative panel interface in the host.
See [rpi-run-stats](packages/rpi-run-stats/README.md) for measurement definitions.

```powershell
cargo test --workspace
cargo build --release --workspace
task install
```

`task install` copies the platform cdylibs to
`~/.rpi/agent/extensions`. The CLI discovers that directory automatically; an
explicit directory also works:

```powershell
rpi --extensions-dir "$HOME/.rpi/agent/extensions"
```

These are `cdylib` extensions, so plain `cargo install` is not the right
consumer installation mechanism. The cross-platform consumer command is built
into the `rpi` host:

```powershell
rpi install rpi-todo
rpi install rpi-todo --version 0.2.0
```

`rpi-im-message` can run the Feishu/Lark long-connection server headlessly,
without opening the TUI:

```powershell
rpi --im-message-server --im-profile feishu-main
```

The profile is optional when `defaultProfile` is set in `.rpi/im.json` (or
`~/.rpi/agent/im.json`). Set the app secret through the profile's environment
variable before starting the process.

The command downloads the crate from crates.io, compiles its cdylib for the
current OS and architecture, and places it in `~/.rpi/agent/extensions`.
After publishing a release, users who prefer prebuilt binaries can download the
platform-specific archive generated by CI and run the installer it ships with.
The archive is self-contained: it carries the extension libraries, the catalog
and the `rpi-package-install` binary itself, so no shell script is involved.

```bash
# Linux / macOS
tar -xzf rpi-packages-linux-x86_64.tar.gz
cd rpi-packages-linux-x86_64
./rpi-package-install install --source-dir .
```

```powershell
# Windows
Expand-Archive .\rpi-packages-windows-x86_64.zip .
cd .\rpi-packages-windows-x86_64
.\rpi-package-install.exe install --source-dir .
```

Developers can instead clone this repository and run `task install`; the package
workspace uses the already published `rpi-plugin-sdk` only, so a sibling
`pi-rust` checkout is not needed.

To install an already-downloaded archive without unpacking it by hand:

```bash
task install-bundle ARCHIVE=dist/rpi-packages-windows-x86_64.zip
```

The optional `task smoke` maintainer check exercises the host loader and does
require a sibling `pi-rust` checkout.

## Automatic crate releases

Every push or PR merge to `main` runs
`.github/workflows/release-cargo.yml`. release-plz compares the workspace with
crates.io, updates versions and package changelogs for unpublished changes,
and synchronizes `catalog/packages.json`. Ordinary changes to the current
`0.x` packages get a patch bump; conventional breaking-change commits can
increase the minor version. Packages inheriting the workspace version share
that version. Already prepared, unpublished versions are preserved.
Release analysis includes history after the migration to registry SDK
dependencies; older commits requiring an external `pi-rust` checkout are
excluded in the CI checkout so historical package comparisons can run.

The workflow tests the workspace and dry-runs Cargo publishing before creating
and merging a version PR. It respects protected `main` without directly pushing
to it. It then publishes unpublished extension crates and creates per-package
tags (`<package>-v<version>`) and GitHub Releases.
The installer is excluded because it has `publish = false`. Publishing runs
in the same workflow as the version update. Runs are serialized, and a failed
release can be retried from the Actions UI or with `workflow_dispatch` on `main`.

Configure the repository Actions secret `CARGO_REGISTRY_TOKEN` with crates.io
publishing permission for all extension crates, including permission to create
any names that have not been published yet. The workflow's `GITHUB_TOKEN` needs
permission to create and merge the version PR and create tags/releases. Enable
Actions PR creation in the repository settings. If branch rules require
approvals or checks, the version PR must satisfy them before releasing.
If organization policy blocks Actions PR creation, set the optional
`RELEASE_GITHUB_TOKEN` secret with repository Contents and Pull requests write
permissions instead.

After crate publishing, `release-assets.yml` automatically builds Windows x64,
Linux x64/ARM64, and macOS Intel/Apple Silicon binaries from the exact release
commit. Each package Release receives individual extension archives and an
`rpi-extension.json` manifest with download URLs, SHA-256 hashes, target triples,
library names and SDK ABI. A separate bundle Release contains the full
collection, installer and standalone ACP bridge. The existing
`release-unix.yml` manual entry point now uses the same five-platform pipeline.

Host developers can implement prebuilt installation using the
[distribution protocol](docs/prebuilt-distribution.md) and its
[JSON schema](docs/rpi-extension.schema.json). Discover the repository from
crates.io metadata, then use the requested package's versioned Release manifest;
packages in this repository do not all share one version.

For a local release preflight, run `task publish-dry-run`. Manual crates.io
publishing requires `cargo login` and an unpublished package version. Each
extension is self-contained and can be published in any order.
`task pack` also creates a directly installable platform bundle under `dist/`
for a GitHub Release or another binary registry.
