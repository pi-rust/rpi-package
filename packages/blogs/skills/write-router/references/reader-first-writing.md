# 读者导向的标题、内容与图解技巧

本规范来自用户对博客文章的明确反馈，是本仓库后续写作、改写和终稿质检的默认标准。与主模式配合使用，不替代事实检索、去 AI 味（`humanizer.md`）、读者共情（`empathy-pass.md`）和发布确认流程。用户对单篇文章另有要求时，以该篇的明确要求为准。

## 总原则

标题吸引读者，内容带读者理解，配图提供证据，流程图解释关系。四者服务于同一个阅读目标，不能各做各的。

低门槛不等于低准确性；有吸引力不等于夸大；图多不等于解释清楚。没有配图价值时不强行配图，不设图片或流程图数量指标。

## 一、标题：点击动机与内容承诺

- 从读者的问题、困惑、使用场景或阅读收益出发，让陌生读者也知道为什么值得看。
- 避免仅用“项目名 + 源码分析”“协议名 + 报文解析”等技术目录式命名。项目名和准确范围可放在摘要或正文中。
- 可以有“标题党”意识：制造好奇心、降低心理门槛，但不得夸大、制造恐慌或虚构经历。
- 降低陌生术语密度；需要保留的关键词必须有助于读者判断主题。
- 标题提出的问题必须由正文回答。不得为了点击率承诺正文并未提供的效果。
- “小学生也能听懂”之类反馈应理解为低门槛目标，不自动写成真实教学经历或绝对效果保证。

示例（用来说明策略，不要求所有文章套用）：

| 目录式表达 | 读者导向表达 |
| --- | --- |
| Langfuse 报文解析 | 如果要给 Agent 搭一套可观测平台，应该从哪里开始？ |
| Agent Loop 源码解读 | Agent 源码看不懂？先跟着一条消息走一遍 |

拟标题前先回答：读者有什么问题？读完能理解或完成什么？正文是否兑现这个承诺？

## 二、内容：按理解顺序组织

- 不默认读者认识项目或工具。先说对象是什么、解决什么问题、为什么值得了解、本文覆盖什么，再进入版本、协议、代码和细节。
- 按读者理解顺序组织，不照搬源码文件顺序或作者调试顺序。版本迁移、历史差异、特殊报错若不是主问题，放到后面的补充部分。
- 围绕一条明确主线展开：一个任务、一条消息、一次请求或一个具体问题。主线讲清楚后再展开支线，必要时把复杂支线留给下一篇。
- 术语第一次出现时说明作用，用熟悉的动作、具体例子或数据解释；不要用另一个陌生术语替代解释。
- 讲清因果、职责与边界：谁提出请求，谁执行，谁转换数据，谁保存，谁显示；不要把不同层的工作归给同一个组件。
- 代码片段和数字例子各回答一个问题。对易误读处，优先使用前后状态、具体计算或正误对照。
- 假设任务、示意格式、源码摘录和实测记录明确区分。不得把教学例子写成亲历或实测。
- 实现结论核对源码，并提供文件、函数或固定版本链接；不同供应商、版本和调用路径的行为不泛化为通则。
- 简化可以省去外围细节，但不能省掉会改变结论的条件。正常路径图不能被表述为完整运行机制。

正文自检：一个第一次接触主题的人，能否说清“是什么、为什么、谁来做、怎么做、到哪里为止”？

- 不默认使用“问题—背景—原理—实践—边界—结论”。可以从一个判断、错误、反常结果、失败经历、具体场景或争议切入。
- 技术文章通常围绕一个主问题，但不要求每篇文章都使用相同的线性章节。允许必要的对比、回看和节奏变化，只要读者知道它们为什么出现。
- 连续三个小节都在解释概念时，应加入例子、对比、数据或作者判断；同一个结论完整解释一次即可，后续引用，不要反复总结。
- 如果背景、术语或反例不会改变读者对主问题的理解，就删掉、压缩或放到链接中。需要独立展开的旁支留给下一篇。

### 技术文章的主线，而不是模板

技术写作首先追求清楚明白，但清楚不等于把所有相关知识都讲完。先确定读者必须理解的那条主线，再决定哪些内容不写。主线可以是一条请求、一次排错、一个反常数据，也可以是作者对某个选择的判断。

构思时可以参考以下步骤，而不是机械套用：

1. 用一句话写清读者读完应该明白什么。
2. 找出理解这个问题真正必需的前置知识。
3. 选择一个贯穿任务、错误、例子或数据。
4. 给每节写一句“本节改变了读者的什么理解”；没有变化就删掉或合并。
5. 主线讲清后再补充会改变结论的条件和边界，其他延伸内容从正文移出。

准确不等于完整，完整不等于值得读。

```text
调用栈原本保存什么
→ 等待时为什么占住处理线程
→ 让本次调用返回后，进度放在哪里
→ 事件到来后如何根据状态继续
→ 手写状态有什么代价，编译器能代劳什么
```

这只是组织方法，不要求所有技术文章使用同一套章节。单线结构允许必要的对比、分支和回看，关键是它们都回到同一个主问题，读者知道当前在解释什么以及下一步为什么出现。

**复杂主题的处理：**原文建议将星状或层次结构的复杂问题拆成多篇、每篇讲透一点。本项目优先在同一篇内收窄范围、重排主线、压缩旁支或使用补充章节；只有用户明确同意才拆篇，不擅自扩展已有文章。文学、历史或多观点分析也不强制改成教程式的单线结构。

**结构预警：**章节按查资料顺序排列；概念尚未解释就跳到另一个概念；历史、源码、性能同时成为平行主线；例子脱离主问题；读者不知道此节在讲原因、过程还是结论。出现这些问题，应先重做骨架，再润色语言。

## 三、配图：证据与阅读引导

- 截图优先使用用户授权提供的真实界面、运行结果或错误现场。没有实际素材时请求素材或明确使用示意图，不伪造截图证据。
- 每张图承担一个任务：证明现象、定位操作、展示结果或解释关键字段。不要为凑数量配图。
- 图放在相关论述附近，避免集中堆在文末。
- 裁剪无关区域，保留理解证据所需的上下文；必要时加编号、框选或局部放大，避免整屏缩小后文字难辨。
- 图注说明读者要看哪里、能得出什么，以及必要的版本和来源边界。不能让截图证明它并未展示的任务或能力。
- 脱敏账号、密钥、私人路径和敏感内容，不篡改关键结果。优先截取最小必要区域。
- 检查实际页面中的尺寸、清晰度和排版；文件存在或插入成功不等于可读。

## 四、流程图：先确定问题，再选择图形

流程图不是把段落装进方框。绘图前写清：这张图要帮读者理解什么？

### 选择表达形式

| 要回答的问题 | 适合的图形 |
| --- | --- |
| 谁负责什么、边界在哪里？ | 分层图、组件图、职责地图 |
| 什么条件走哪条路？ | 分支图 |
| 数据怎么变化、为何没有丢失或重复？ | 状态图、正误对照图 |
| 谁先调用谁、结果怎么回来？ | 时序图 |
| 为什么还要再次请求、怎样形成循环？ | 闭环图 |

### 设计要求

- 一张图突出一个重点，不混装完整架构、调用顺序、数据流和全部异常处理。
- 用分组和阶段建立阅读路径，主线优先，支线弱化。适量使用编号、粗箭头和颜色；不能只靠颜色区分含义。
- 节点写清动作或状态，箭头标明传递的数据、触发条件或关系。避免只有函数名、没有含义的方框。
- 节点短而具体，复杂解释留在正文；需要时主动换行，不把整段文字塞进节点。
- 减少参与者和交叉箭头。合并角色时说明合并范围，不能掩盖关键职责差异。
- 复杂内容拆图，不以“画全了”为目标。概念分工图不得让读者误以为它是严格执行时序。
- 突出容易误解的关系，例如模型提出调用而程序执行、消息已在 context 中、工具结果需进入下一次请求。
- 图前提示阅读重点，图后解释关键结论与省略范围。避免把图中每个节点再机械复述一遍。

### 渲染验收

- 使用博客现有支持的 Mermaid 写法，核对当前渲染器兼容性，不只检查代码围栏和语法。
- 在实际预览中检查文字、间距、箭头标签、交叉线、宽高比例和缩放效果，特别留意横向过宽导致字体缩小。
- 文字不得被节点边框、连线、背景或其他标签遮挡，不得因正文样式覆盖字体、字号或行高而溢出、裁切或无法辨认。
- 分别检查正文和点击放大后的视图；放大视图中的样式、字体和文字容器也必须保持正确。出现遮挡时先定位布局、容器裁切或样式冲突，再修复并复查，不以“成功渲染”作为问题已解决的依据。
- 长图、参与者过多或多分支图优先重新布局、简化或拆分，不用放大功能替代正常阅读下的可读性。
- 关注桌面和窄屏表现。不能完成某种显示环境的验证时，明确说明未验证，不声称已经通过。
- 区分语法检查、成功渲染与视觉验收；只执行了前两者，不能报告已完成视觉验收。

## URL 展示：地址直接可见

- 文章外链必须能找到完整、可复制且可点击的 URL。短地址直接展示；长地址可以用有意义的文字链接，并在就近说明或参考资料另列完整地址。优先使用 `来源：<https://example.com/>` 或 `[https://example.com/path](https://example.com/path)`。
- 不用仅含“官网”“文档”“详情”等标签的链接隐藏地址；正文、图注、表格、参考资料和文末入口都要遵守。
- 链接文字与实际目标一致，保留协议、域名和完整路径，不用省略号截断。长 URL 应通过排版自动换行，不在地址中插入字符。
- 图片嵌入和代码保留原有语法；不要为了显示地址破坏图片加载或代码执行。
- 投稿适配时复查链接，防止平台将完整 URL 替换成不可见的文字卡片。

## 五、统一验收

- 标题让读者愿意进来，且正文兑现承诺。
- 正文让不熟悉背景的读者跟得上，技术细节仍可核验。
- 截图让读者看得到依据，来源、隐私和图注边界清楚。
- 图解让读者看得清关系，不只是增加方框和箭头。

删掉一张图后，如果文章没有损失信息、证据或理解上的帮助，就重新设计或删除它。
