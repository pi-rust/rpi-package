# 读者共情与温度写作

这是所有文章都要使用的读者方法，读取与复核时点由 `.rpi/SYSTEM.md` 决定。完整写作在成文设计前明确读者入口与阻力，写作中落实，返修与验收时复查；局部任务只处理授权范围。它不仅检查文章是否好懂，还检查读者能否找到愿意继续读下去的理解路径。

## 共情不是讨好

读者共情不是增加“你是不是也……”这类句子，也不是替读者编造经历。它要求文章认真处理读者的处境、知识差距、顾虑、选择成本和情绪负担。

文章的“温度”也不是情绪词的数量，而是作者是否愿意为读者承担一部分理解成本：提前说明入口，拆开难点，解释为什么这样安排，并在容易失败的地方给出边界。换句话说，温度是共情落实到结构、解释和语气之后的结果，不是另加的一层修辞。

## 核心方法：陪伴式解释

原有的“五步检查”回答“读者需要什么”；下面的“陪伴式解释”回答“正文怎样把这些需要写出来”。两者合并使用，不是增加一套独立流程：

**共同定位 → 共同拆解 → 共同判断 → 留下出口**。

这四项是解释任务，不是每节必须出现的句式或小标题，也不要求使用“我们”。技术文可以通过例子和失败路径完成；文学与历史可通过人物处境、细节和叙事顺序完成，不强加操作步骤或教学口吻。

### 1. 共同定位：让读者知道我们从哪里开始

开头或章节转折处，明确当前要解决的问题、阅读入口和暂时不处理的内容：

> 我们先从这个简单例子入手。暂时不看完整 ABI 定义，只看一次调用怎样创建、轮询和销毁。

这里的“我们”是包容性的第一人称，不是声称作者和读者有相同经历，而是邀请读者沿着同一条理解路径前进。适合用于：

- 进入陌生主题时；
- 从一个抽象概念切换到具体例子时；
- 章节之间需要重新定位时；
- 需要告诉读者“现在不用一次理解全部内容”时。

### 2. 共同拆解：把复杂任务变成可以跟随的动作

不要只罗列知识点，要写清我们先看什么、为什么先看它、看完之后怎样进入下一层：

> 我们把这条链分成两个时间点：先看动态库如何进入注册表，再看注册表中的函数表如何驱动一次调用。

技术文、源码分析和教程尤其适合使用这种写法。它把作者的知识顺序改造成读者可以执行的阅读顺序，降低面对长源码、陌生术语和版本差异时的压力。

### 3. 共同判断：让结论和依据一起出现

“我们”不能替代证据，也不能把作者的判断伪装成集体共识。应该把共同观察和事实边界放在一起：

> 我们看这段代码时，重点不是返回了哪句文本，而是指针的生命周期。

随后必须给出代码、数据、失败路径或来源，说明这个判断凭什么成立。涉及安全、性能、版本行为和历史事实时，优先使用事实陈述：

> `destroy` 只能在宿主不再调用 `poll` 后执行。

而不是用“我们都知道”“我们需要注意”来增加语气。

### 4. 留下出口：告诉读者接下来可以怎样做

温度最终要落到行动和选择上，而不是停留在亲切语气：

- 指出下一步应该打开哪个文件或运行哪个命令；
- 说明照做失败时先检查版本、路径还是输入；
- 说明当前结论适用于什么条件，不适用于什么场景；
- 给出继续深入的入口，但不把所有旁支都塞进本文。

例如：

> 我们读 demo 时可以分两遍：第一遍只看状态如何创建、完成、取消和释放；第二遍再看 SDK 怎样把它包装成 ABI 函数表。

## “我们”的使用边界

### 适合使用

- “我们先……”：安排理解顺序；
- “我们可以从……”：提供低门槛入口；
- “我们把……分成……”：拆解复杂流程；
- “我们读源码时……”：给出阅读策略；
- “当我们看到……时……”：引导读者观察具体证据。

### 不宜滥用

不要每段都用“我们可以看到”，也不要用“我们”替读者编造经历：

> 不宜：我们第一次遇到这个问题时，肯定会以为是 Rust 类型不兼容。
>
> 更稳妥：这里要区分 Rust 类型是否兼容，以及跨动态库边界的布局和所有权约定；本节先核对后者。

也不要用“我们都知道”包装未经证明的判断。事实、风险、限制和结论应直接说清楚。

### 使用比例

“我们”应集中在入口、转折、拆解和行动建议处，而不是平均撒在全文。一个简单检查标准是：删掉某个“我们”后，句子的事实和逻辑是否仍然成立？

- 如果删掉后只是少了陪伴感，可以保留；
- 如果删掉后句子更准确、更有力，就不要为了温度保留；
- 如果文章只有“我们”而没有具体场景、证据和出口，说明温度还停留在语气层面。

## 五步检查：把陪伴式解释落到稿件

五步检查负责审读实际文章；上面的四个动作负责把检查结果落实到正文。它们不是两套互相竞争的方法，而是“发现问题”和“修改文章”的关系。

### 1. 找到读者进入文章的瞬间

- 他为什么现在点开？
- 他最想先知道什么？
- 开头是否从他的具体问题进入，而不是从宏大背景进入？

### 2. 识别读者阻力

- 他可能不懂哪个术语？
- 他可能在哪一步失败？
- 他会怀疑什么？
- 他担心投入时间、金钱、风险还是被误导？

### 3. 把抽象判断落地

用场景、错误、选择、人物处境、时间成本、失败后果和真实代价解释抽象观点。

### 4. 调整解释顺序

先解决读者最急的问题，再补充背景。不要把最有用的信息埋在最后，也不要用作者的知识顺序替代读者的理解顺序。

### 5. 给出读者能带走的东西

可以是：

- 一套可执行步骤
- 一个减少试错的判断标准
- 对人物或历史的更准确理解
- 对争议问题的判断框架
- 一种被理解的感觉
- 下一步行动

## 按题材检查

| 题材 | 需要回应的读者处境 |
|---|---|
| 技术 | 版本不一致、报错焦虑、文档缺口、照做仍失败 |
| 日志 | 看不到过程、担心失败、想知道决策和返工的真实代价 |
| 长文 | 对复杂议题感到混乱、被口号淹没、需要判断依据 |
| 源码分析 | 不知道入口、看不懂调用链、无法把局部代码连成整体 |
| 历史人物 | 容易站在结果之后评判、缺少时代背景和约束 |
| 其他 | 根据具体受众的知识、情绪和行动需求定制 |

## 最终提问

> 如果我就是目标读者，读到这里会觉得作者真的理解我的问题吗？

如果答案是否定的，先改结构、例子和解释，不要只加情绪词。
