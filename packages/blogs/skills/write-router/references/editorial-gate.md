# 具体审稿与返修

审稿要改变或验证成稿，不是宣称“已审”。初稿写完，再切换到编辑视角读完整文章，将结果补入 `.rpi/writing/<article-slug>/work.md` 的“编辑返修”。

本文件负责内容与事实、结构、标题、图表和阅读负担的问题定位。语言自然度与可读性的返修方法见 `humanizer.md`，读者路径与温度的检查见 `empathy-pass.md`，两者由 `.rpi/SYSTEM.md` 编排为独立阶段；本文件在这一步只需指出语言问题的位置和依据，改动在那里执行并记录。

## 首先读成稿，不先看检查表

用几句话说清：它回答了什么，主要依据是什么，读者现在多理解了什么。说不清就先调整主线。接着找最影响文章质量的具体位置，按以下顺序处理：

先读实际文章，再对照来源，最后回看作者的工作底稿；不要让底稿中的自评替你判断。不要只抽几句核对正确就放行整篇。通读各节，检查每节给读者增加了什么；同一答案换措辞反复出现时合并，知识旁支若不改变本篇判断就压缩。关键事实回到已读取的来源核验，工作底稿是核验线索，不能替代原始证据。

## 复杂技术稿的深度闸门

以下检查适用于源码分析、架构比较、机制解释、评测和排错文章；短摘要、标题、局部润色不强行套用。它是内容审稿的前置闸门，不是给审稿表增加几个勾选项：闸门未过，必须回到成文设计或正文返修，不能靠机器检查、增加链接或润色放行。

1. **先校准比较对象和层级**：写下每个对象“负责什么、不负责什么、与谁相邻”。如果两者不在同一抽象层，文章必须明确比较的是哪一层，以及读者为什么仍然需要把它们放在一起看。禁止用“更简单／更灵活／更重”作为没有机制解释的结论。
2. **用同一个具体动作走双路径**：为每个中心比较选择一个可复现动作（例如同一个工具调用、请求或事件），分别记录入口函数、状态/上下文组装、核心调用、扩展边界、结果写回、停止条件和清理路径。每条路径至少落到可定位的函数、接口、事件、服务或源码位置；只写模块名、目录名或概念名不算追踪。
3. **逐层回答“谁承担不变量”**：对取消、顺序、并发、错误、重试、持久化、依赖就绪和生命周期等判断，写出实际承担者及触发条件。若某个不变量由多个组件共同完成，要说明协作关系；若源码没有保证，明确写成未保证或需上层承担。
4. **检查证据—解释—选择的闭环**：每个主章节至少有一处具体证据、一段把证据翻译成读者理解的解释，以及一个影响设计选择/适用边界的结论。代码位置本身不是解释，表格也不能替代因果关系。
5. **做反泛化复读**：圈出只说“适合大型项目”“更容易扩展”“复杂度更高”等句子，逐句追问删掉后读者是否失去一个可验证事实；若不会，删掉或改成具体机制。对同一结论在摘要、正文和结尾的重复，保留一次最有证据的位置。
6. **确认标题承诺兑现**：标题说“源码”“调用链”“从简单到深入”或“比较”时，正文必须实际展示对应的调用顺序、边界和差异，不得仅用架构名词或优缺点表替代。

在 `work.md` 记录这次闸门的实际结果：比较对象/层级、选定动作、两条路径的入口与终点、至少两个关键不变量及其承担者、未解决缺口。只写“已完成深度审稿”不算记录。

核验“某规范说明……”时，找到实际章节和原文片段，用 source_quote_check 检查缓存中的片段，再读上下文判断支持关系。合理的工程推理也不能伪装成规范原话。匹配成功不代表语义成立；代码示意还要核对实际动作、参数和竞态，不只看语法。

1. **论断站不住**：来源不足、口径混合、猜测写成事实、标题夸大。补证据、改判断或缩范围，不靠免责声明放行。
2. **有资料而没有解释**：事实罗列、读者看不出为什么、结尾只说“结合实际”。补关键因果、对照、计算或场景，不能仅加更多概念。
3. **主线没有推进**：各节只是主题分类，反复解释同一结论。重排、合并或删去支线，保留影响结论的条件。
4. **具体内容被磨平**：泛化开头、套话替代观察、重要例子/失败/核验入口丢失。恢复有信息价值的内容，不为流畅牺牲准确性。
5. **语言与阅读负担**：术语未解释、超长句、插入语套插入语、机械问句与列表化、用“值得一说／值得注意的是”代替内容、粗体与破折号当节奏工具。这一项按 `humanizer.md` 的线索定位并标出原句，改动在下一阶段执行；不要把它当“最后润色”，长句和术语堆积同样会让读者读到一半放弃。

文学按人物、细节、视角和节奏审读；不能将这些问题强制转换成论文式论证。

## 审稿结果写到具体文字

错误示范：“结构清晰，事实可靠，已 Humanizer，共情通过。”

可核查的结果：
- “第二节把‘高度吻合的一种解释’写成‘已经确定的原因’。恢复推断限定，并写清缺少哪份历史记录。”
- “第三、五节都在说明‘更多连接不等于更多吞吐’。合并重复解释，保留第三节的具体量级计算。”
- “第四节只报差异，没说明测量的是已完成响应。把统计对象放在表前，否则读者会误解 P99 的范围。”
- “初稿‘这是很多 agent 项目做不到的一点’改成‘这一点值得单独说，因为……’，未核实的比较删掉了，元话语却带进来了。替换句直接写内容：‘`rpi-ai` 把真实的 HTTP provider 放在 `providers` feature flag 后面，默认构建里没有网络栈，测试套件不可能依赖网络。’”

每项记原句/位置、问题或核验依据、如何处理、复查结果。不要求虚构缺点或固定改几轮。没有发现需改处时，记录实际核验的关键判断与证据位置，不能只填“无问题”。

实际修改项增加定稿中的替换句或具体新位置。逐项核对：原句确实来自初稿、替换句确实出现在定稿、问题是否解决。不能在审稿表里宣称实施了定稿没有发生的修改；这种不一致本身就是未完成返修。

引用原句时保持连续、逐字一致，跨段内容分开记录，不将列表去掉符号后拼成一条“原句”。教学示意同样核对条件判断方向、日期与星期、单位和字段关系；标成示意不能掩盖自身矛盾。

## 返修后再验收

实际工作分步执行：保存初稿 → 重新读取 → 写出具体修改 → 用 draft_revise / edit 修改原文件 → 再次读取定稿。修改工具的 applied 结果证明替换执行，不能证明编辑判断正确，仍需阅读修改后的段落。工作记录引用文件里的实际文字，不引用计划中尚未落地的版本。

检查修改是否解决原问题、是否改变事实强度、是否引入新的重复、断裂、元话语或超长句。关键事实待核实、中心问题没回答、核心解释仍空泛时，不交付为终稿。缺工具或材料时准确说明未完成的环节。

再对照加工稿中的解释：它们在正文哪一句落实了？只出现在底稿或审稿表中不算写出来。对有数量关系的材料，能解释结果的必要量级关系应写清；只将“数字增加”复述成“等待增加”没有补足解释。其他题材同样检查关键因果、对照或叙事动作是否真正落在正文。

没有原稿也必须对照材料加工稿审读；有原稿再检查改稿是否保住有效证据、具体观察、事实限定与作者声音。风格样稿不提供本篇事实。

稿子合格的依据是具体内容：有明确问题、有支撑答案的材料、有写出来的解释、结构推进、语气和题材匹配。字数、图数、链接数和打勾次数不是质量分。

审稿与后续验收的顺序由 `.rpi/SYSTEM.md` 系统提示词统一编排。本文件提供具体审稿方法；blog-qa 提供机器、外链、渲染和视觉检查方法，各自记录实际范围。机器通过不能替代编辑验收。对于复杂技术稿，必须另外记录深度闸门的双路径和不变量结果；没有这些具体内容，不得用“结构清晰”或“已核实”结案。

draft_compare 仅辅助有原稿的任务，提示明显损失；合理摘要标 summarize，纯风格参考标 style。不要为消除提示机械补数字、图和链接。
