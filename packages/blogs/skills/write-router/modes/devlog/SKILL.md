# Devlog Writing Mode

## 适用

用于开发日志、项目记录、功能构建过程、AI 协作记录、调试复盘和迭代故事。

## 文章目标

让读者看到成果背后的过程：约束、选择、错误、返工、协作和判断，而不是只看文件清单。

## 推荐结构

```text
当时要解决什么
→ 原有状态和约束
→ 初始方案
→ 决策、分歧或误解
→ 实现过程
→ 调试、失败和返工
→ 最终结果
→ 技术与协作复盘
```

## 素材提取

从 session、提交记录、问题单或笔记中保留：

- 人类的目标、限制和纠正
- AI 或团队提出的方案
- 同意、拒绝和改方向的节点
- 错误信息、失败尝试和修复
- 长时间自主执行和关键人工介入
- 最终方案与最初方案的差异

不要把工具输出原样塞进文章，工具输出只作为证据。

## 写法

- 决策是故事的核心：写清为什么选、谁推动、后来是否改变。
- 诚实写错误和过度设计，不把过程伪装成一次成功。
- 代码只是佐料，放 5 到 15 行解释一个关键点。
- AI 协作文章可以用“我”和“我的 human”，普通团队日志则用真实角色称呼。
- 需要时加入一张 Mermaid 图解释架构或请求流，不为装饰而加图。
- 结尾写双方或团队学到了什么，以及下一次会怎么做。

## 事实边界

- 不虚构没有发生的争论、心理活动或惊喜。
- 不把工具调用推断成人类意图。
- 不把最终代码的结果倒灌成当时必然知道的选择。
- session 不完整时，明确写“现有记录显示”或删除该细节。

## 模式自检

- 读者是否能感到过程，而不是只看到总结？
- 是否写清了最重要的决策和转折？
- 失败和返工是否带来理解，而不是单纯卖惨？
- 人和 AI 各自贡献了什么，是否说清楚？

当前题材任务完成后，由 `.rpi/SYSTEM.md` 系统提示词决定下一阶段及返工；本模式只提供开发记录的具体写法。
