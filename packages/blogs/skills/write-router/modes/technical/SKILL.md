# 技术文章

目标是让读者理解具体问题、能完成任务，或能基于证据与取舍作判断。

## 按内容任务组织

- **评测**：先说比较对象和问题，再交代影响结论的条件、关键结果、反常现象与解释。保留统计口径、失败样本、核验与复现入口；不能压成通用选型建议。
- **机制解释**：选择一条请求、状态变化或具体动作，让读者看清谁做什么、数据怎样变化、为何出现该结果。必要概念随例子引入。
- **排错/实践**：从真实症状与影响进入，呈现证据如何排除可能原因，以及解决方案为什么有效。失败尝试只有推动判断时才保留。
- **教程**：说明前置条件、操作、预期结果和失败处理，关键步骤必须能核验。
- **方案比较**：围绕实际约束比较代价、收益与适用边界；不先罗列全部功能再用“结合实际”收尾。

这些是组织方向，不是章节模板。按材料加工稿决定入口和承接；不要求所有文章从环境列表开场，不强行补“原理、实践、总结”。

## 写正文

对象的用途和文章范围要让读者及时知道；环境、版本和输入放在影响解释的位置。用具体数据、错误、动作、代码或对照支撑判断，再解释这些材料意味着什么。代码前后说明它解决哪个问题，必要术语随用随解释。

完整改稿要保住论证价值，不是把原稿再展开一遍。结果表只在承担论证任务的位置展示；开头可以预告判断，但不要在开头、详解和结尾重复整张表。机制沿一个例子讲清一次，后面引用结论。用连贯段落表达解释与判断，列表留给真正并列的事项和操作，不把段落逐句拆成条目。

说明性例子、源码摘录和真实实测分别标记。单次成功不写成普遍规律；没有证据不编使用时长、收益、机制归因或性能数字。

场景名称不是瓶颈证据：“HTTP/JSON”不自动等于“I/O 密集”，CPU 占满也不能定位到某个函数，内存差额不自动都是 GC。把观测结果、机制假说和已验证归因分开；没有剖析材料时可以解释量级和可检验的可能性，不替实验完成归因。

## 题材审读要点

评测核对口径与证据保留；教程核对可执行性。不得只改句子、不补解释。当前题材任务完成后，由系统提示词决定下一阶段及返工，不在本模式另设终稿流程。
